In this lesson, we'll explore how the Website Builder works from a developer's perspective, then get the Next.js starter kit running locally and create a first page — confirming the full stack is wired up correctly.

**Prerequisites:**

- A running Webiny project (completed via the Getting Started chapter, or already deployed)
- Node.js 22+ and npm/yarn installed (Node.js 24+ still required for Webiny CLI — if you're only working with the Next.js side, 22+ is sufficient)
- Familiarity with Next.js App Router — the starter kit uses App Router, not Pages Router

## How It All Fits Together

Before we start writing any code, it's worth taking a moment to understand how the Website Builder actually works — because it's a bit different from what you might expect.

When a content editor opens the Website Builder in Webiny Admin, they see a canvas where they can drag components onto a page, configure their inputs in a sidebar, and hit Publish. That's the editorial experience.

<Image
    src="/learn/images/lessons/foundation/webiny-website-builder.png"
    title="Website Builder - Page editor"
/>

On the developer side, the picture is a bit different — and it's what makes the Website Builder stand out from most page builders.

**The editor doesn't have its own components or styles.** Instead, it's always connected to a separate frontend app that you own — in our case a Next.js project. When the editor opens, it loads your Next.js app inside an iframe. The component palette, the live preview, all of it is your real app running right there.

This means all your component code and all your styles live in your Next.js project. Webiny only stores the page structure — which components are on the page and what input values the editor set for each one. It has no idea what a "Hero" or "Banner" looks like, and it never needs to.

<Callout type="info">
    We'll cover how to create and register your own editor components in the next lesson.
</Callout>

The practical upside: no style clashes, no fighting the platform, full ownership of your code. And because editors are looking at your actual app, the WYSIWYG is genuine — not a simulation.

```txt title="Architecture diagram"
┌──────────────────────────────────────────────────────────┐
│  Webiny Admin                                            │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │  Website Builder Editor                            │  │
│  │                                                    │  │
│  │   sidebar     ┌──────────────────────────────┐     │  │
│  │   (inputs)    │  your Next.js app (iframe)   │     │  │
│  │               │  real components             │     │  │
│  │               │  real styles                 │     │  │
│  │               └──────────────────────────────┘     │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
                        ↕ postMessage (SDK)
┌──────────────────────────────────────────────────────────┐
│  Your Next.js App (running separately)                   │
│  @webiny/sdk-nextjs SDK installed                        │
└──────────────────────────────────────────────────────────┘
```

The `@webiny/sdk-nextjs` SDK is what connects the two sides — it handles the communication between the editor and your app when editing, and fetches published page documents from Webiny when rendering pages for visitors.

With that in mind, let's get everything set up.

## Step 1: Start the Admin App

You'll need the Webiny Admin app running before creating pages later in this lesson. Get it going now so it's ready when you need it.

- **Locally:** run `yarn webiny watch admin` in your Webiny project directory.
- **Deployed environment:** use the Admin CloudFront URL directly — no local command needed.

## Step 2: Clone the Starter Kit

Webiny provides starter kits that wire up the SDK, routing, and rendering so you have a working base to build from. There are starter kits for Next.js and Nuxt; this course uses the Next.js one. The official Next.js starter kit lives at [github.com/webiny/website-builder-nextjs](https://github.com/webiny/website-builder-nextjs). Each Webiny release line has its own branch, so clone the one that matches your Webiny version (`starter-kit-6.5.x` for Webiny 6.5):

```bash title="Terminal"
git clone -b starter-kit-6.5.x https://github.com/webiny/website-builder-nextjs.git my-website
cd my-website
npm install
```

Before running `npm install`, make sure `package.json` lists `@webiny/sdk-nextjs` with a version that matches your Webiny version. You can find it by running `webiny --version` in your Webiny project.

For example, if your Webiny version is `6.5.1`, your `package.json` should have (the `~` allows patch updates, which are safe):

```json title="package.json"
{
  "dependencies": {
    "@webiny/sdk-nextjs": "~6.5.1"
  }
}
```

## Step 3: Gather Your Credentials

To connect the starter kit to your Webiny project, you'll need an API key, API host URL, and tenant ID. The easiest way to get these is through the **Configure Frontend** shortcut in Webiny Admin: open **Dev Tools** in the main menu and select **Configure Frontend**.

    caption="Open Dev Tools and select Configure Frontend"
/>

A dialog appears with a **Next.js** tab that has the three environment variables already filled in and ready to copy:

<Image
    src="/learn/images/website-builder/configure-nextjs-dialog.png"
    alt="Configure Frontend dialog showing NEXT_PUBLIC_WEBINY_API_KEY, NEXT_PUBLIC_WEBINY_API_HOST, and NEXT_PUBLIC_WEBINY_API_TENANT pre-filled"
    caption="The Configure Frontend dialog gives you all three values in one click"
/>

Click the copy icon and paste the block directly into your `.env` file in the next step.

The dialog also has a **Frontend Domain** field. This is the URL the editor loads in its iframe, and it defaults to `http://localhost:3000`, which is where the starter kit's dev server runs. Change it only if your app runs somewhere else.

<Callout type="info">
    If your Admin is running on a non-localhost domain (i.e. a deployed CloudFront URL), the dialog
    will also include a `NEXT_PUBLIC_WEBINY_ADMIN_HOST` variable — make sure to copy that
    too. The starter kit adds it to the `frame-ancestors` header in `next.config.ts`, which allows
    that Admin to load your app in the editor iframe.
</Callout>

### API Key Is Auto-Created

Note that unlike the Headless CMS chapter where you had to manually create an API key and configure its permissions, the Website Builder API key is created automatically for the current tenant — you'll find it under **Settings → Access Management → API Keys** as "Frontend Integration". It's a read-only key, intentionally scoped that way since it's meant to be used in external frontend apps like your Next.js project. The Configure Frontend dialog pulls it for you, so there's nothing to set up manually.

## Step 4: Configure Environment Variables

Create a `.env` file in the root of your Next.js project:

```dotenv title=".env"
NEXT_PUBLIC_WEBINY_API_KEY=your_api_key_here
NEXT_PUBLIC_WEBINY_API_HOST=https://your-cloudfront-url.cloudfront.net
NEXT_PUBLIC_WEBINY_API_TENANT=root
```

<Callout type="hint">
    All three variables are prefixed with `NEXT_PUBLIC_` because they are used on the client side
    during live editing. The Content SDK also reads them server-side at build/request time.
</Callout>

## How the Rendering Works

The starter kit's catch-all route (`app/(site)/[[...slug]]/page.tsx`) handles all page rendering:

```typescript title="app/(site)/[[...slug]]/page.tsx (simplified)"
export default async function Page({ params, searchParams }) {
  const { slug = [] } = await params;
  const search = await searchParams;

  // Initialize the SDK with credentials from env vars
  const previewMode = await draftMode();
  initializeSdk({ preview: previewMode.isEnabled, tenantId: await getTenant() });

  // Is the page loaded inside the Website Builder editor?
  const isEditing = search["wb.editing"] === "true";

  // Fetch the page document from Webiny
  const result = await sdk.wb.getPage(normalizeSlug(slug));
  const page = result.isOk() ? result.value : null;

  // DocumentRenderer maps component names → your React components
  return <DocumentRenderer document={page} isEditing={isEditing} />;
}
```

`initializeSdk` (in `sdk/initializeSdk.ts`) calls `sdk.init()` with your env var credentials and passes in the theme and the component groups. `DocumentRenderer` takes the page document (a JSON tree of component names and their input values) and renders it by looking up each name in your registered `editorComponents` array.

## Troubleshooting

### Still seeing "Page not found" after publishing

- Make sure you set the page **path** to `/` exactly.
- Check the browser console for API errors — a CORS or auth error means your env vars may be wrong.
- Restart the dev server after editing `.env`.

### Editor shows a blank canvas

- Make sure your Next.js dev server is running on the URL set as **Frontend Domain** in the Configure Frontend dialog (`http://localhost:3000` by default).

## Summary

- The Website Builder editor loads your Next.js app in an iframe — components and styles live entirely in your project.
