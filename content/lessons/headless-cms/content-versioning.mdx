# Content Versioning

In this lesson, we'll explore how Webiny handles content versioning. Webiny's versioning system is designed to give you full control over your content lifecycle, from drafts to published versions, with the ability to track changes and revert when needed.

## What Is Content Versioning?

**Content versioning** is a system that tracks changes to your content entries over time. Every time you modify an entry, Webiny creates a new version (also called a "revision") while preserving the previous versions.

Think of it like version control (Git) for your content:

- Each save creates a new version
- You can view the history of changes
- You can revert to previous versions
- You can have unpublished drafts alongside published content

<Callout type="info" title="Non-Destructive Editing">
  With Webiny's versioning system, you never lose content. Every change is
  tracked, and you can always revert to a previous version if needed.
</Callout>

## Key Concepts

### Revisions

A **revision** is a snapshot of your content at a specific point in time. Every time you save changes to an entry, Webiny creates a new revision.

For example, if you create a blog post and save it 5 times while editing, you'll have 5 revisions:

- Revision 1: Initial draft
- Revision 2: Added introduction
- Revision 3: Added main content
- Revision 4: Added images
- Revision 5: Fixed typos

Each revision is numbered and timestamped, making it easy to track the evolution of your content.

### Published vs Unpublished

Revisions can be in one of two states:

- **Unpublished (Draft)** - Content that exists but is not publicly available
- **Published** - Content that is live and accessible via the public API

This separation is crucial because it allows you to:

- Work on changes without affecting the live content
- Preview changes before publishing
- Maintain a published version while working on updates

<Callout type="hint" title="Safe Editing">
  You can edit a published entry without affecting what's live. Your changes
  create a new unpublished revision, and the published version remains unchanged
  until you explicitly publish the new revision.
</Callout>

## The Content Lifecycle

Let's walk through the typical lifecycle of a content entry:

### 1. Create a New Entry

When you create a new entry, it starts as **revision 1** in an **unpublished** state.

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
```

At this point, the entry exists but is not accessible via the public Read API.

### 2. Make Changes

Every time you save changes, a new revision is created:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Unpublished)
```

All revisions remain unpublished. The public API still doesn't return this entry.

### 3. Publish

When you're ready to make your content public, you publish the latest revision:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Published) ← Currently published version
```

Now the entry is accessible via the Read API, and users can see revision 3.

### 4. Edit Published Content

When you edit a published entry, new revisions are created but remain unpublished:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Published) ← Still the published version
├─ Revision 4 (Unpublished)
├─ Revision 5 (Unpublished)
```

The published version (revision 3) remains live while you work on revisions 4 and 5.

### 5. Publish Updates

When you publish revision 5, it becomes the new published version:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Previously published)
├─ Revision 4 (Unpublished)
├─ Revision 5 (Published) ← Now the published version
```

Revision 3 is no longer published, but it's still preserved in the history.

<Callout type="success" title="One Published Version at a Time">
  Only one revision can be published at a time. When you publish a new revision,
  it automatically replaces the previously published version.
</Callout>

## Unpublishing Content

You can also unpublish content, which removes it from the public API:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Unpublished) ← No longer published
├─ Revision 4 (Unpublished)
├─ Revision 5 (Unpublished)
```

The entry still exists with all its revisions, but none are published, so it won't appear in the public API.

## Revision Management

### Viewing Revision History

In the Webiny Admin UI, you can:

- View the list of all revisions for an entry
- See who created each revision and when
- Compare different revisions
- Restore a previous revision

### Restoring Previous Revisions

If you need to revert to a previous version:

1. Select the revision you want to restore
2. Click "Restore" or "Create from this revision"
3. A new revision is created based on the selected one

This doesn't delete newer revisions - it creates a new revision with the old content.

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Published)
├─ Revision 4 (Unpublished) ← Made a mistake here
├─ Revision 5 (Unpublished) ← Restore revision 3
```

After restoring revision 3, you get:

```
Entry: "My Blog Post"
├─ Revision 1 (Unpublished)
├─ Revision 2 (Unpublished)
├─ Revision 3 (Published)
├─ Revision 4 (Unpublished)
├─ Revision 5 (Unpublished) ← Copy of revision 3
```

## Different APIs See Different Versions

Webiny provides multiple APIs that behave differently regarding versioning:

- **Read API** - Returns only published entries
- **Preview API** - Returns the latest revision (published or unpublished)
- **Manage API** - Full access to all revisions

We'll explore these APIs in detail in a later lesson, but it's important to understand that versioning is tightly integrated with how these APIs work.

<Callout type="info" title="Preview Before Publishing">
  The Preview API is perfect for "preview mode" in your frontend application. It
  lets editors see their changes before publishing, without making them public.
</Callout>

## Best Practices

### 1. Save Often

Don't be afraid to save frequently. Each save creates a new revision, giving you more granular history to fall back on if needed.

### 2. Use Descriptive Changes

While Webiny tracks revisions automatically, it's good practice to make meaningful changes between saves, making the revision history more useful.

### 3. Preview Before Publishing

Always use the Preview API or preview mode to review changes before publishing them to production.

### 4. Don't Delete Published Content Immediately

If you need to remove content, unpublish it first and monitor for a while before deleting. This gives you a safety net in case you need to restore it.

## Why Versioning Matters

Content versioning provides several critical benefits:

1. **Safety** - Never lose content due to accidental changes
2. **Flexibility** - Work on updates without affecting live content
3. **Audit Trail** - Track who changed what and when
4. **Rollback Capability** - Revert to previous versions when needed
5. **Workflow Support** - Separate draft and published states enable editorial workflows

## Summary

Webiny's content versioning system provides powerful content management capabilities:

- **Every save creates a revision** - Complete history of all changes
- **Published vs unpublished states** - Safe editing without affecting live content
- **One published version at a time** - Clear separation between draft and live
- **Non-destructive editing** - Never lose previous versions
- **Restore capability** - Revert to any previous revision

This versioning system is the foundation for safe, professional content management. In the next lesson, we'll put this knowledge into practice by creating your first content model through the Webiny Admin UI.
